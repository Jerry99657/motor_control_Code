# STM32H743 AVI/MJPEG 播放故障修复与排查指南

## 1. 文档目的

本文记录本工程 AVI/MJPEG 播放故障的现象、定位过程、最终解决方案，以及以后排查类似问题时建议采用的方法。

本次问题并非单一缺陷，而是 JPEG 解码、DMA 回调、Cache、FatFs/SDMMC 读取和界面错误显示等多个问题叠加。修复过程中出现过以下典型现象：

- 点击 `.avi` 后 LCD 黑屏，MCU 卡死，按键无响应。
- 播放立即退出并显示 `failed(-6)`。
- 成功播放 1～2 秒后退出并显示 `failed(-5)`。
- 播放数秒后 SD 卡目录显示 `Empty`，之后无法继续读取文件。
- 优化 SD 读取后可播放约 37 秒，但仍偶发卡顿并以 `failed(-5)` 退出。
- 最终改为 MJPEG 播放期间使用多扇区轮询读取后，可正常播放完整 AVI 文件。

涉及的主要文件：

- `Drivers/User/Src/mjpeg_player.c`
- `Drivers/User/Inc/mjpeg_player.h`
- `FATFS/Target/sd_diskio.c`
- `FATFS/Target/sd_diskio.h`
- `Drivers/User/Src/lvgl_app.c`
- `Core/Inc/jpeg_utils_conf.h`

## 2. 播放链路

本工程中的 AVI/MJPEG 播放链路如下：

```text
FatFs 打开 AVI
    ↓
解析 RIFF / LIST / hdrl / movi
    ↓
从 SD 卡读取一个 JPEG 压缩帧
    ↓
STM32 JPEG 外设通过 DMA 解码
    ↓
jpeg_utils 将 YCbCr 转换为 RGB565
    ↓
RGB565 帧进入共享媒体内存池
    ↓
SPI6/BDMA 将图像发送到 LCD
```

调试时应按这条链路逐层隔离。不要看到 LCD 黑屏就直接判断为 LCD 故障，也不要看到 `failed(-5)` 就直接判断 AVI 文件格式错误。

## 3. 错误码含义

播放器错误码定义在 `Drivers/User/Inc/mjpeg_player.h`。

| 错误码 | 含义 | 优先检查方向 |
| --- | --- | --- |
| `0` | 播放成功或正常到达文件尾 | 无 |
| `-1` | 参数错误 | 文件路径、空指针 |
| `-2` | SD 挂载失败 | FatFs、SD 卡状态、SDMMC 初始化 |
| `-3` | 文件打开失败 | 路径、文件名、挂载状态 |
| `-4` | AVI/MJPEG 格式错误 | RIFF/LIST/movi、块长度、视频流编号 |
| `-5` | 文件读取或定位失败 | `f_read()`、`f_lseek()`、SDMMC、FatFs |
| `-6` | JPEG 解码失败 | JPEG DMA、回调、颜色转换、输入完整性 |
| `-7` | KEY2 主动停止 | 正常用户操作 |
| `-8` | 不支持的 JPEG 格式或尺寸 | 采样格式、分辨率、颜色格式 |
| `-9` | 单帧过大 | 压缩帧缓冲区容量 |
| `-10` | 共享媒体内存池忙 | 内存所有者未释放或并发播放 |
| `-11` | KEY3 返回 | 正常用户操作 |

界面还会显示 FatFs 的附加错误码，例如：

```text
MJPEG failed(-5, fs=1)
```

其中常见的 `fs` 值为：

| `fs` | FatFs 结果 | 含义 |
| --- | --- | --- |
| `0` | `FR_OK` | 没有记录到底层磁盘错误，应继续检查短读、EOF 或播放器状态机 |
| `1` | `FR_DISK_ERR` | SD 底层读写失败 |
| `2` | `FR_INT_ERR` | FatFs 内部状态异常 |
| `3` | `FR_NOT_READY` | SD 卡或磁盘驱动未就绪 |

## 4. 本次问题的关键根因

### 4.1 JPEG 输出颜色格式与 LCD 不一致

LCD 使用 RGB565，而早期 JPEG 配置输出 ARGB8888。两者每像素字节数不同，容易造成转换长度错误、输出缓冲区越界或显示数据解释错误。

最终配置：

```c
#define JPEG_RGB_FORMAT JPEG_RGB565
```

同时播放器增加了编译期检查，防止配置被 CubeMX 或其他修改重新覆盖后静默产生内存错误。

### 4.2 `jpeg_utils` 解码输出计数不可靠

当前使用的 ST `jpeg_utils` 版本在解码路径中可能返回 `ConvertedDataCount == 0`，原因是内部使用了主要面向编码路径的 `BlockSize` 字段。

如果播放器把零值直接视为“没有转换任何数据”，就会立即返回 `failed(-6)`。

最终处理方式是以实际转换的 MCU 数量和已知 MCU 输入大小为依据，推导已经消耗的字节数，同时允许最后一个 MCU 后存在少量对齐填充字节。

### 4.3 不应在 JPEG 中断回调中执行阻塞式 Abort

在 JPEG DMA 回调中调用 `HAL_JPEG_Abort()` 可能引入回调重入、HAL 状态机锁死或长时间占用中断的问题。

当前原则：

- 中断回调只更新状态、记录计数、提交下一块 DMA。
- 超时和错误恢复放在主线程的解码控制流程中执行。
- 所有等待必须有超时，不能无限等待回调标志。

### 4.4 AVI 不能假设 `movi` 内只有连续视频块

实际 AVI 文件可能包含：

- `LIST/rec ` 嵌套块；
- 视频流块，例如 `00dc`、`01dc`；
- 音频块，例如 `01wb`；
- 奇数长度块和一个字节的对齐填充；
- 文件末尾的 `idx1` 等索引数据。

播放器因此使用有边界的 LIST/rec 迭代器，只接受目标视频流，并使用以下方式计算下一个块：

```text
data_pos  = chunk_pos + 8
chunk_end = data_pos + chunk_size
next_pos  = chunk_end + (chunk_size & 1)
```

每一步都检查加法溢出以及是否超过当前容器边界。

### 4.5 文件尾短读曾被误判为 I/O 错误

`f_read()` 返回 `FR_OK`，但读取字节数小于请求字节数，通常表示到达文件尾，并不等同于 SD 卡故障。

旧实现将下面两种情况都映射为 `-5`：

- `f_read()` 返回非 `FR_OK`；
- `f_read()` 返回 `FR_OK`，但发生文件尾短读。

最终将两者分开：

- `fr != FR_OK`：真正的 I/O 错误；
- `read_len != requested_len`：返回 EOF；
- AVI 容器剩余空间不足 8 字节块头时，也按正常容器结束处理。

### 4.6 SD DMA 完成标志存在竞态

DMA 启动后再清除 `ReadStatus` 会产生竞态：

```text
启动 DMA
    ↓
DMA 很快完成，中断把 ReadStatus 设为 1
    ↓
主线程随后把 ReadStatus 清零
    ↓
完成事件永久丢失，主线程等待到超时
```

正确顺序是先清除完成标志，再启动 DMA：

```c
ReadStatus = 0U;
BSP_SD_ReadBlocks_DMA(...);
```

错误回调和 Abort 回调会将状态设为独立的错误值，使等待循环可以及时退出。

### 4.7 `HAL_SD_Abort()` 不足以恢复所有 SDMMC 错误

发生 SDMMC/IDMA 错误后，仅调用 `HAL_SD_Abort()` 可能仍然留下：

- HAL 句柄处于 BUSY 或 ERROR；
- SDMMC 内部状态未清除；
- 挂起的 SDMMC 中断；
- SD 卡未回到 TRANSFER 状态。

本工程的完整恢复流程为：

1. `HAL_SD_Abort()`；
2. `HAL_SD_DeInit()`；
3. 清除 `SDMMC1_IRQn` 挂起状态；
4. 对 SDMMC1 执行 RCC 强制复位和释放复位；
5. `BSP_SD_Init()` 重新初始化卡并恢复四位总线；
6. 等待卡回到 `SD_TRANSFER_OK`；
7. 恢复失败时设置 `STA_NOINIT`，使 FatFs 下次挂载重新初始化磁盘。

### 4.8 AVI 的非对齐小块读取不适合逐扇区 DMA

这是本次 `failed(-5)` 最关键的稳定性问题。

BIN 动画通常使用对齐的大块连续读取，而 AVI 的块头、音频块、视频帧和填充字节会使文件位置频繁变成非 32 字节对齐。FatFs 最终可能向 `disk_read()` 传入非对齐目标地址。

旧的兼容路径使用 512 字节暂存区，并为每一个扇区单独启动一次 DMA。播放 MJPEG 时会产生大量短 DMA 操作。实际测试表现为：

- 最初只能播放 1～2 秒；
- 调整暂存读取后延长到数秒或约 37 秒；
- 长时间运行后仍可能发生 SDMMC/IDMA 错误并返回 `FR_DISK_ERR`。

最终方案：

- 暂存区扩大到 4 KB，即 8 个扇区；
- 非对齐读取按最多 8 个扇区批量处理；
- MJPEG 播放期间通过 `SD_SetReadPollingMode(1)` 强制所有 SD 读取使用轮询模式；
- 播放结束和所有提前退出路径都调用 `SD_SetReadPollingMode(0)`，恢复普通 DMA 模式；
- 普通文件浏览和 BIN 播放仍可使用 DMA；
- 轮询读取失败时仍执行一次完整 SDMMC 重初始化并重试。

该方案是稳定性和性能之间的折中。MJPEG 播放器本身运行在同步主线程中，轮询读取会占用主线程，但不会关闭中断，因此高优先级电机控制和安全中断仍可执行。

如果未来必须让 MJPEG 的 SD 读取也使用 DMA，建议在播放器层建立两个固定地址、固定大小、32 字节对齐的读缓冲区，并在媒体层实现双缓冲预取，不要让 FatFs 将任意非对齐目标地址直接交给高频单扇区 DMA。

### 4.9 Cache 维护必须与实际传输方式匹配

DMA 从外设写入 RAM 后，需要失效对应的 D-Cache；CPU 轮询读取写入缓存后，则不能直接执行相同的 DMA 失效流程，否则可能丢弃 CPU 刚写入但尚未清理到 RAM 的数据。

本工程遵循以下规则：

- DMA 读取前：对目标区域执行必要的 Clean/Invalidate；
- DMA 完成后：Invalidate，确保 CPU 看到 DMA 写入的数据；
- CPU 轮询读取：直接使用 CPU 写入的数据，不套用 DMA 完成后的失效路径；
- 如果轮询读取作为 DMA 路径的恢复分支，并且外层仍会失效 Cache，则先将 CPU 写入的数据 Clean 到 RAM。

此外，所有 DMA 缓冲区都应检查：

- 地址是否至少 4 字节对齐；
- 使用 Cache 维护时是否 32 字节对齐；
- 所在 SRAM 区域是否可被对应 DMA 控制器访问；
- Cache 维护长度是否覆盖完整缓存行。

### 4.10 `Empty` 曾掩盖真实 SD 错误

文件浏览器原来在扫描结果为零时无条件显示：

```text
Empty: /path
```

但零条目可能来自两种完全不同的情况：

- 目录确实为空；
- `f_mount()`、`f_opendir()` 或 `f_readdir()` 失败。

最终增加独立的目录扫描结果 `s_browser_scan_result`。只有 `FR_OK` 且条目数为零时才显示 Empty；否则显示真实扫描错误。MJPEG 播放结果也在页面重建后重新写入，避免被目录刷新覆盖。

## 5. 推荐的 MJPEG 故障排查流程

### 第一步：固定测试条件

准备以下测试资源：

- 一个已经确认可在 PC 正常播放的 AVI/MJPEG 文件；
- 一个短视频和一个至少一分钟的长视频；
- 一个已知正常的 BIN 动画；
- 固定的 SD 卡和供电条件。

每次只改变一个变量，并记录：

- 点击播放后多久失败；
- 最后一帧画面是否完整；
- MCU 是否仍响应按键和中断；
- LCD 错误码和 `fs` 错误码；
- 退出后能否重新扫描 SD 目录。

“每次都在同一时间或同一帧失败”更像文件结构或特定帧问题；“失败时间变化很大”更像 DMA、Cache、竞争条件或硬件信号完整性问题。

### 第二步：判断 MCU 卡死还是播放器主动退出

如果按键、SysTick 和调试器全部无响应，应优先检查：

- HardFault、BusFault、MemManage Fault；
- 无限等待 DMA 标志；
- 中断中执行阻塞 HAL API；
- 栈溢出或缓冲区越界。

如果页面能够返回并显示错误码，说明主循环仍在运行，应沿错误码对应的返回路径检查，而不是先排查 HardFault。

### 第三步：分离 SD 读取与 JPEG 解码

建议依次进行以下隔离实验：

1. 只打开 AVI 并遍历块，不执行 JPEG 解码和 LCD 显示。
2. 只读取并保存第一帧长度，确认 SOI `FFD8` 和 EOI `FFD9`。
3. 固定解码第一帧，重复播放同一帧，不继续读取 SD。
4. JPEG 解码成功后暂时不发送 LCD，只检查输出长度和图像尺寸。
5. LCD 暂时使用阻塞发送，排除显示 DMA 流水线问题。
6. SD 暂时使用轮询读取，排除 SD IDMA 和 Cache 问题。

判断方法：

- 固定第一帧仍失败：重点检查 JPEG 解码和输出缓冲区。
- 不显示 LCD 时稳定：重点检查 SPI/BDMA、LCD 缓冲区所有权。
- SD 改轮询后稳定：重点检查 SD DMA、对齐、Cache 和完成回调。
- 只遍历 AVI 就失败：重点检查 FatFs 和 AVI 块边界。

### 第四步：检查 AVI 容器边界

对每个块至少记录：

```text
当前位置 pos
块 FourCC
chunk_size
chunk_next
当前 LIST 结束位置
目标视频流编号
```

必须验证：

- `chunk_next` 没有整数溢出；
- `chunk_next` 不超过当前容器结束位置；
- 奇数块长度跳过一个填充字节；
- `LIST` 的前四字节是列表类型，不是普通负载；
- 音频块被正确跳过；
- 视频流编号与 `strl/strh` 中识别的 MJPG 视频流一致；
- 当前容器不足 8 字节块头时按 EOF/容器结束处理。

可以在 PC 上使用 `ffprobe` 或其他 AVI 分析工具先确认编码格式、分辨率、帧率、视频流编号和文件时长，再与 MCU 解析结果比较。

### 第五步：检查 JPEG DMA 回调状态

建议记录以下计数和状态，但不要在每个中断中打印大量日志：

- `InfoReady` 回调次数；
- `GetData` 回调次数；
- `DataReady` 回调次数；
- Error 回调次数；
- 输入当前位置与剩余长度；
- 输出块长度；
- 已转换 MCU 数与总 MCU 数；
- HAL JPEG 状态和错误码；
- 是否因软件超时退出。

典型判断：

- 没有 `InfoReady`：JPEG 头不完整、输入错误或 DMA 未运行。
- 有 `InfoReady`，没有 `DataReady`：输出 DMA、JPEG IRQ 或输出缓冲区问题。
- 有一次 `DataReady` 后失败：重点检查颜色转换、输出计数和回调中的 Abort。
- 回调都正常但 LCD 黑屏：检查 RGB 格式、字节序和 LCD 传输。

日志必须限频。串口日志过多会改变中断时序，甚至造成日志缓冲区溢出，让问题更难复现。

### 第六步：检查 SDMMC/FatFs

对 `failed(-5)` 应记录：

- `f_read()` 的 `FRESULT`；
- 实际读取长度和请求长度；
- `FIL.err`；
- `HAL_SD_GetState()`；
- `HAL_SD_GetCardState()`；
- `HAL_SD_GetError()`；
- 当前扇区、扇区数量和目标缓冲区地址；
- DMA 完成、Abort 和 Error 回调状态。

重点检查：

- DMA 完成标志是否在启动 DMA 前清零；
- SDMMC 中断优先级是否能够及时响应；
- 等待循环是否有有限超时；
- 目标地址是否满足 DMA 对齐要求；
- 非对齐 FatFs 缓冲区是否经过安全暂存区；
- 是否在一次读取尚未完成时启动下一次读取；
- 出错后是否只 Abort，却没有重新初始化卡和外设；
- FatFs 短读是否被错误当成磁盘错误。

### 第七步：检查内存和 Cache

使用链接器 map 文件确认每个大缓冲区的实际地址，而不是只看源代码中的 section 名称。

需要确认：

- JPEG 输入、输出缓冲区容量是否覆盖最坏情况；
- RGB565 输出容量至少为 `width * height * 2`；
- 压缩帧长度没有超过输入缓冲区；
- 共享媒体内存池在退出路径中一定释放；
- SDMMC、JPEG、MDMA、DMA2D、SPI6/BDMA 能访问对应 SRAM；
- D2/D3 非缓存区配置与链接器段地址一致；
- Cache Clean/Invalidate 的地址和长度按 32 字节缓存行对齐。

建议给关键缓冲区前后添加保护字，并在每帧后检查，快速发现越界写入。

### 第八步：检查所有退出和恢复路径

播放器通常存在很多提前退出分支。每一条路径都必须正确完成：

- 等待或停止仍在运行的 LCD DMA；
- 停止 JPEG DMA，并在主线程恢复 HAL 状态；
- 关闭文件；
- 卸载或保持 FatFs 挂载状态的一致性；
- 释放共享媒体内存池；
- 恢复 SD 普通读取模式；
- 清理全局 `active/done/error` 标志；
- 返回真实错误码，不能被页面刷新覆盖。

建议尽量使用统一的 `cleanup` 出口，减少遗漏恢复步骤。

## 6. 本工程的最终稳定方案摘要

本工程最终采用以下组合方案：

1. JPEG 输出统一为 RGB565。
2. 严格检查视频尺寸、帧长度和所有缓冲区容量。
3. 修正 `jpeg_utils` 解码输出计数，按实际 MCU 数量计算消耗量。
4. JPEG 中断回调中不执行阻塞式 Abort。
5. AVI 使用支持嵌套 `LIST/rec ` 的有界迭代器。
6. 正确处理奇数块填充、目标视频流和文件尾短读。
7. SD DMA 完成标志在启动 DMA 前清零。
8. SD 错误时执行完整 SDMMC 外设和卡重初始化。
9. 非对齐 SD 读取使用 4 KB、32 字节对齐的暂存区批量读取。
10. MJPEG 播放期间强制使用 SD 多扇区轮询读取，播放结束后恢复 DMA。
11. DMA 和轮询路径分别执行正确的 Cache 维护。
12. 文件浏览器区分真实空目录和 SD 扫描失败。
13. UI 同时显示播放器错误码和 FatFs 错误码。

## 7. 回归测试清单

每次修改 MJPEG、FatFs、Cache、链接器脚本或 DMA 配置后，至少完成以下测试：

- 连续播放同一 AVI 三次，确认每次都正常结束。
- 播放超过一分钟的 AVI。
- 在 AVI 播放中按 KEY3，确认能够返回文件列表且 SD 目录仍可访问。
- 在 AVI 播放中按 KEY2，确认能够执行全局停止并退出播放。
- 播放结束后立即播放 BIN、GIF 和另一个 AVI。
- 测试带音频流、无音频流以及包含 `LIST/rec ` 的 AVI。
- 测试奇数长度块和不同帧大小的文件。
- 确认电机实时控制和安全中断在播放期间仍正常运行。
- 开启和关闭 D-Cache 分别进行一次基础验证。
- 检查共享媒体内存池所有者在退出后回到 `MEDIA_MEMORY_OWNER_NONE`。
- 检查长时间播放后 RAM、栈和 DMA 状态没有逐帧累积。

## 8. 后续优化建议

当前轮询方案以稳定性优先。若后续需要提高分辨率或帧率，可按以下顺序优化：

1. 在媒体层建立两个固定的 32 字节对齐 SD 读缓冲区。
2. 只允许 SD DMA 写入这两个已知、可访问、Cache 策略明确的缓冲区。
3. 使用双缓冲，让 SD 预取下一帧与当前帧 JPEG 解码/LCD 发送重叠。
4. 用事件状态机替代长时间忙等，但保留有限超时和错误恢复。
5. 对每个阶段统计耗时、最大耗时和超时次数。
6. 完成至少数小时的循环播放压力测试后，再将 DMA 路径设为默认。

不要直接恢复“任意 FatFs 目标地址逐扇区 DMA”的实现，否则非对齐访问、Cache 和高频 IDMA 启停问题很可能再次出现。
